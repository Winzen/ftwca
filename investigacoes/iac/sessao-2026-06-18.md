## 2. Redução de cache Loki + retenção de 6 meses

### Contexto
Cache do Loki usava defaults do chart (8192 MB + 1024 MB) muito acima do uso real. Sem retenção configurada, o PVC de 100Gi encheria em ~10 meses.

### Arquivos alterados
**Branch IAC:** `feat/reduce-observability-resources` | **PR:** iac#137

`k8s/observability/loki/values.yaml`:
- `chunksCache.allocatedMemory`: 8192 → **512**
- `resultsCache.allocatedMemory`: 1024 → **64**
- Adicionado `loki.limits_config.retention_period: 4320h` (6 meses)
- Adicionado `loki.compactor.retention_enabled: true`

### Recursos liberados
| Recurso | Liberado |
|---|---|
| Memória (cache Loki) | ~8.5Gi |

## 4. Override de recursos por deployment no work pool

### Contexto
Flows `br_anatel_telefonia_movel` morriam com OOMKilled. O work pool tinha `resources` hardcoded no template — qualquer `job_variables` no deployment era **ignorado silenciosamente**.

### O que foi feito
Substituímos os valores hardcoded por variáveis Jinja nos dois work pools (`basedosdados` e `basedosdados-dev`):

```json
// antes
"resources": {"limits": {"memory": "4Gi"}, "requests": {"memory": "1Gi"}}

// depois
"resources": {"limits": {"memory": "{{ memory_limit }}"}, "requests": {"memory": "{{ memory_request }}"}}
```

Variáveis adicionadas ao schema com os mesmos valores como defaults:

| Variável | Default |
|---|---|
| `memory_limit` | `4Gi` |
| `memory_request` | `1Gi` |
| `cpu_limit` | `2` |
| `cpu_request` | `500m` |

Todos os flows existentes continuam com o mesmo comportamento — apenas flows que declararem `job_variables` recebem valores diferentes.

### Armadilha descoberta
`{{ memory_limit | default('4Gi') }}` **não funciona** — o Kubernetes recebe a string literal e rejeita o job com erro de validação. O default deve estar no schema, não no template.

## 5. Fix OOM br_anatel_telefonia_movel

### Diagnóstico
| Tentativa | Resultado |
|---|---|
| Rodar com limit padrão (4Gi) | OOMKilled — o zip da Anatel precisa de mais de 4Gi |
| Setar `job_variables: {resources: {...}}` via API | Ignorado — template hardcoded |
| Setar `customizations` com JSON patch | Ignorado — worker não aplica |
| Mudar template para variáveis Jinja + `job_variables: {memory_limit: "8Gi"}` | ✅ Funcionou |

### Testes individuais
| Flow | Resultado com 8Gi |
|---|---|
| `densidade_brasil` | ✅ Completed |
| `microdados` | ✅ Completed |
| `densidade_municipio` | ✅ Completed |
| `densidade_uf` | ✅ Completed |

### Descoberta: Eviction vs OOMKilled
Ao rodar 3 flows simultâneos (8Gi cada), um foi **evicted** por pressão de memória no nó — não OOMKilled. O kubelet matou o pod com menor margem entre uso e request quando o nó ficou com apenas 37MB livres. São erros diferentes com soluções diferentes:

- **OOMKilled** → aumentar `memory_limit`
- **Eviction** → distribuir schedules para não rodar ao mesmo tempo

### Fix definitivo
**Branch pipelines:** `fix/anatel-telefonia-movel-oom` | **PR:** pipelines#1581 | **Issue:** pipelines#1582

Dois arquivos alterados:

**`.github/scripts/deploy_flows.py`**
- Adicionado suporte a `flow.job_variables` — lê o atributo e passa para `.deploy(job_variables=...)`

**`pipelines/datasets/br_anatel_telefonia_movel/flows.py`**
- Adicionado `_flow.job_variables = {"memory_limit": "8Gi", "memory_request": "2Gi"}` na factory `_anatel_tm_flow`
- Schedules distribuídos por dias da semana para evitar concorrência:

| Flow | Antes | Depois |
|---|---|---|
| `microdados` | todo dia 16:30 | **segunda** 16:30 |
| `densidade_municipio` | todo dia 17:30 | **terça** 16:30 |
| `densidade_uf` | todo dia 18:30 | **quarta** 16:30 |
| `densidade_brasil` | todo dia 19:30 | **quinta** 16:30 |

### Status atual
4 flows pausados aguardando merge do PR#1581. Após merge, o CI redeploya com 8Gi e os schedules corretos — daí despausar os 4.
